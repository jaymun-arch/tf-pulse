## 1. 문서 목적

이 문서는 **현재 구현된 TF Pulse가 무엇을 관리하기 위해 만들어졌는지**를 정의하고,  
동시에 **재구성 시 참고할 보완점**을 제시한다.

- **As-Is**: 지금 코드·화면에 실제로 있는 범위
- **To-Be 제안**: 목표를 더 선명히 하기 위한 개선·재편 후보 (구현 약속이 아님)

재구성 판단 시 우선 읽을 섹션: **2. 관리 목표**, **8. 보완점·재구성 제안**.

## 2. 관리 목표 (Why this product exists)

### 2.1 한 줄 정의

**연성대학교 혁신지원사업 관련 보고서 TF**가  
「목차 할당 → 취합 → 윤독 → 예산(계획/실적) → 일정·요청 → 서식·도식」을  
**한 허브에서 역할별로 운영**할 수 있게 하는 웹앱.

### 2.2 핵심 관리 영역 (의도된 관리 대상)

| # | 관리 영역 | 관리하려는 것 | 성공 기준(의도) |
|---|-----------|---------------|-----------------|
| M1 | **보고서 작성 운영** | 목차·페이지·담당자 할당, 차수별 취합 제출 | 누가 몇 페이지를 맡았는지·제출했는지 즉시 파악 |
| M2 | **품질·윤독** | PDF/문서 기반 요약·코멘트·리뷰 태그 | 윤독 회의 전에 핵심 내용·수치·환류를 공유 |
| M3 | **예산·실적 이원화** | 운영계획(편성) vs 결과보고(실적) 입력 | 계획용/실적용 수치·산출내역을 혼동 없이 취합 |
| M4 | **TF 운영 커뮤니케이션** | 공통 요청, 마감·일정 알림 | 미처리 요청·다가오는 일정을 놓치지 않음 |
| M5 | **산출물·서식 지원** | 드라이브/공통서식, 레이아웃·도식 PPT, AI 브리핑 | 보고서 문장·그림을 빠르게 보조 |
| M6 | **팀 운영 부가** | 식사 돌림판·투표 (사기/운영 편의) | TF 중 가벼운 의사결정 지원 (핵심 업무는 아님) |

### 2.3 명시적으로 “하지 않는” 것 (현재 범위 밖)

- 교육부·대학 공식 결재/전자문서 시스템 대체
- 다기관 동시 접속을 전제로 한 실시간 협업 서버(현재는 브라우저 로컬 저장 중심)
- 회계 ERP·예산 집행 승인 시스템
- 완성본 HWP 자동 생성(도식·레이아웃 PPT 보조에 가깝다)

## 3. 제품 개요

### 3.1 제품명·맥락

- **제품명**: TF Pulse  
- **맥락**: 2026 교육혁신(혁신지원사업) 성과/계획 관련 보고서 TF 운영  
- **형태**: 정적 프론트엔드 + (선택) OpenAI API 서버리스/로컬 API  
- **데이터**: 기본적으로 `localStorage` (`tf-ops-data-v10`), 관리자 JSON 내보내기·가져오기

### 3.2 사용자(역할)

| 역할 | 코드상 role | 주요 권한 |
|------|-------------|-----------|
| 관리자 | `admin` | 목차·할당, 대상자, 공통 요청, AI 취합분석, JSON 백업, 설정 메뉴 |
| 예산담당 | `budget` | 예산 항목 취합·통계·엑셀 등 예산 관리 |
| 식사담당 | `food` | 업체·메뉴·돌림판 공지·투표 |
| 대상자(작성자) | `member` | 담당 파트 취합, 요청 처리, 배정 예산 산출, 그림 활용 |

접속 방식: **이름 선택 로그인**(계정/비밀번호 없음). UI·메뉴는 역할에 따라 제한.

### 3.3 정보 구조(메뉴)

```
홈
보고서 ─┬─ 취합
        ├─ 윤독·리뷰
        └─ 그림
운영 ───┬─ 일정
        ├─ 요청
        └─ 오늘 뭐먹지
예산
자료 ───┬─ 드라이브
        ├─ 공통 서식
        └─ 사용방법
설정(관리자) ─┬─ 목차·할당
              └─ 대상자
```

## 4. 이해관계자·운영 시나리오

### 4.1 이해관계자

| 이해관계자 | 관심사 |
|------------|--------|
| TF 총괄(관리자) | 진도·미제출·요청 미처리·예산 편성률 한눈에 |
| 파트 작성자 | 내 할당·취합 입력·요청·내 예산만 집중 |
| 예산 실무 | 편성/실적 분리 입력·취합·엑셀 |
| 윤독 참석자 | PDF 요약·코멘트 흐름 |
| (간접) 보고서 독자/평가 | 앱 밖 — 앱은 “만드는 과정”을 지원 |

### 4.2 대표 시나리오 (As-Is)

1. **킥오프**: 관리자가 대상자·목차·페이지·담당자를 세팅한다.  
2. **작성·취합**: 작성자가 차수별 취합에 페이지/상태를 올리고, 관리자는 AI 브리핑으로 초안을 점검한다.  
3. **윤독**: 파트 PDF를 올려 요약표를 만들고 회의 코멘트를 남긴다.  
4. **예산**: 운영계획(예산) 탭에서 편성·산출을, 결과보고(실적) 탭에서 실적·산출을 입력한다.  
5. **마감 운영**: 일정·공통 요청·알람으로 독촉한다.  
6. **도식 보조**: 레이아웃 PPT 1종 선택 다운로드, 또는 GPT 기획 기반 편집용 도식 PPT/참고 이미지.

## 8. 보완점·재구성 제안 (To-Be)

아래는 “현재 수준을 인정한 뒤, 목표를 더 또렷이 하기 위한” 제안이다.  
재구성 시 **한 축을 고르는 것**을 권한다.

### 8.1 목표 선명도 이슈

| 현상 | 위험 | 제안 |
|------|------|------|
| 보고서 운영 + 예산 + 식사 + AI 그림이 한 앱에 공존 | “무엇을 관리하는 앱인지”가 흐려짐 | **코어(보고서·예산·요청)** vs **위성(식사·장식 AI)** 레이어를 문서·IA에서 분리 |
| 운영계획서/결과보고서 구분이 예산·그림에 흩어짐 | 같은 TF인데 문서 종류가 이중으로 느껴짐 | **보고서 시즌 모드(Plan/Result)** 를 전역 토글로 두고 취합·예산·그림이 모두 따르게 |
| localStorage + 이름 로그인 | 공용 PC·다중 작성자 동시 입력에 취약 | “개인 작업대”로 포지셔닝하거나, **관리자 마스터 JSON을 단일 원본**으로 운영 규약화 |

### 8.2 정보구조(IA) 재구성 후보

**후보 A — 문서 생명주기 중심**  
`계획 수립` → `작성·취합` → `윤독` → `실적·결산` → `자료`  
(예산 계획/실적 탭이 단계에 자연스럽게 붙음)

**후보 B — 역할 홈 중심**  
로그인 후 역할별 홈(관리자 관제 / 작성자 할 일 / 예산 할 일)만 먼저 보여 주고, 나머지는 뒤로.

**후보 C — As-Is 유지 + 정리만**  
메뉴는 유지하되, 홈에서 M1~M4 KPI만 강조하고 식사·AI는 “도구”로 강등.

### 8.3 기능 갭 (우선순위 제안)

| 우선순위 | 갭 | 이유 |
|----------|----|------|
| P0 | **단일 원본 데이터**(공유 저장소 또는 강제 JSON 동기 규약) | 지금 구조의 가장 큰 운영 리스크 |
| P0 | 배포본과 로컬 기능 동기화(`plan-diagram` 등) | “AI가 된다/안 된다” 혼란 |
| P1 | 전역 **운영계획서/결과보고서** 모드 | 관리 목표 M3·M5를 한 축으로 |
| P1 | 취합 미제출·요청 미완료 **할 일 리스트** | 홈 수치보다 행동 유도 |
| P2 | 윤독 결과 → 취합/개정 요청 자동 연결 | M2→M1 피드백 루프 |
| P2 | 도식 라벨 ↔ 본문 수치 일치 검증 | AI 산출물 신뢰 |
| P3 | 식사 모듈 분리(별 앱/탭 축소) | 코어 집중 |

### 8.4 품질·거버넌스

- 요구사항 ID(FR-*)를 릴리스 체크리스트에 연결  
- “관리 목표 M1~M4”에 기여하지 않는 신규 기능은 보류 규칙  
- AI는 **초안·보조**, 최종 수치·문장 책임은 담당자임을 UI에 고정 문구

### 8.5 재구성 워크숍용 질문지

1. 이 앱의 1순위 사용자는 **총괄**인가 **작성자**인가?  
2. 데이터 원본은 **개인 브라우저**로 충분한가, **공유 마스터**가 필수인가?  
3. 지금은 **계획 TF**인가 **결과(연차) TF**인가, 둘 다인가?  
4. AI는 **필수 생산수단**인가 **있으면 좋은 도구**인가?  
5. “오늘 뭐먹지”를 공식 범위에 둘 것인가?

답에 따라 섹션 2.2 표의 가중치를 다시 매기면 IA·백로그가 정리된다.

## 9. 수락 기준 예시 (현재 수준 유지 시)

다음을 만족하면 “현재 SRS As-Is 범위의 TF 운영 허브”로 수락 가능하다.

1. 관리자가 파트·담당·대상자를 세팅하고 JSON으로 백업할 수 있다.  
2. 작성자가 담당 취합을 입력하고, 관리자가 차수별 제출 현황을 본다.  
3. 예산에서 계획/실적 모드를 바꿔 입력·조회할 수 있다.  
4. 공통 요청·일정 알람이 동작한다.  
5. (AI 키 있을 때) 취합 분석 또는 도식/이미지 API가 로컬 또는 배포에서 동작한다.
